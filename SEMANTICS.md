# Authorization semantics (rules S1–S13)

> **From v1.3 the normative specification is [`spec/sar-profile.md`](spec/sar-profile.md)** (BCP 14 requirements `SAR-REQ-nnn`, CDDL in `spec/sar-profile.cddl`, test vectors in `spec/test-vectors/`, decision log in `spec/ISSUES.md`). This file keeps the rules S1–S13 as they were resolved in v1.2, with their history. Correspondence: S1, S2 → SAR-REQ-050; S3 → 051; S4 → 052; S5 → 060; S6 → 062; S7 → 024; S8 → 040–042; S9 → 020–023, 032–034; S10 → 080–085; S11 → 100, 101; S12 → 090, 091; S13 → 053, 102. Where this file and the profile differ, the profile wins.


The SARWP paper (§4.5–4.12) leaves several decisions open. A second implementation (`independent/`) was written by a separate instance of the same AI assistant from the paper's Sections 3–4 (v1.1) plus a fixed wire-format specification (`independent/BRIEF.md`), without access to `sar_cose`. It made different choices from `sar_cose` in places. Comparing the two on identical inputs gave **128 disagreements in 6,000 decisions** in the reproducible reconstruction (`tools/reproduce_blind_diff.sh`: `sar_cose` at commit e2e39dd against the reconstructed blind version in `independent/original_blind/`; 118 were reported from the original, unpreserved run). Every one traced to one of the gaps below.

Each rule fixes one reading. Where the paper allows a lenient and a strict reading, the strict one is chosen, following §4.7 ("ambiguous policy results are treated as failures") and invariant I5 (deny by default). The one deliberate exception is the clock tolerance of S1, which is a deployment parameter. Both implementations follow these rules, and `test_sar_cross.py` checks that they agree.

Time is in integer seconds. `SKEW` = 30 s.

| Rule | Decision | Paper basis | Previously in sar_cose |
|---|---|---|---|
| **S1 Clock tolerance** | The clock of the evaluating component may run behind the signers' clocks by at most `SKEW`. A statement dated up to `SKEW` after the evaluation instant is therefore accepted; one dated more than `SKEW` after it is denied. | §4.7 (validity), §3.2 | same |
| **S2 Validity intervals** | Each statement has a nominal half-open interval: a proposal `[issued_at, expires_at)`, a ratification `[reviewed_at, valid_until)`. Empty intervals (`ttl <= 0`) are invalid. The **common interval** of a proposal and its ratifications is `[lo, hi)` with `lo = max(issued_at, reviewed_at…)` and `hi = min(expires_at, valid_until…)`. An evaluation at instant `t` accepts the set iff `lo < hi` and `lo − SKEW <= t < hi`: the tolerance applies to the start only, expiry is exact. | §4.5.1–4.5.2 | inclusive end (`now <= expires_at`); until round 2 of v1.2 the text said `issued_at <= now`, contradicting S1 |
| **S3 Review window** | A ratification must be issued within its proposal's validity: `issued_at <= reviewed_at < expires_at`. | §4.6 phases 1→2; I2 | end of window not checked at the gate |
| **S4 Invalid ratification** | One invalid ratification in the set denies the request, even if the others reach quorum. Invalid means: unauthorized overseer, bad signature, wrong binding or policy, malformed, out of window, **expired**, or unknown verdict. | §4.7 lists "Expired ratification" and "Invalid overseer signature" as denial conditions; §4.6 phase 3 "Any validation failure terminates" | expired approvals were silently not counted |
| **S5 Duplicates** | Two ratifications from the same overseer deny the request. Quorum counts distinct overseers. | §4.5.3 quorum; §4.7 ambiguity → failure | duplicates ignored |
| **S6 Rejection veto** | Any `REJECTED` ratification denies the request, regardless of other approvals. | §4.11, §4.7 "Rejected verdict" | same |
| **S7 Verdicts** | Only the exact strings `APPROVED` and `REJECTED` are valid. Anything else denies. | §4.5.2 | same |
| **S8 Policy validity** | The policy has exactly the keys `policy_id`, `quorum`, `authorized_agents` and `authorized_overseers`. Ids are non-empty strings; keys are valid Ed25519 public keys in lowercase hex; `1 <= quorum <= #overseers`. **Separation of roles:** no key is shared by two overseers, and no identity or key is both an agent and an overseer. Otherwise every request is denied. The policy is read on every request, so removing an agent or overseer (revocation) takes effect for every later request, including requests whose ratification was issued earlier. | §4.5.3; O1 (an *authorized human* ratifies); §4.7 "Invalid … policy" | role separation not enforced (**security gap**: one key under two overseer ids could meet a quorum of 2; an agent listed as overseer could ratify its own proposal) |
| **S9 Statement shape** | Bodies have exactly the v1 field set, with `v = 1`, typed fields and 32-byte digests. `proposal_id` must equal its recomputation: the first 32 hex characters (128 bits) of SHA-256 over the deterministic CBOR of the proposal body without `proposal_id`. The signature is exactly 128 lowercase hex characters. Identifiers and digests are compared exactly (no case folding, all 32 bytes). | §4.5.1–4.5.2; I1 | extra fields and arbitrary `proposal_id` accepted |
| **S10 Replay keys** | An ALLOW atomically consumes `proposal_id`, the nonce (unique per policy, across agents, compared exactly) and, if the payload map has a top-level `transaction_id`, that transaction id, compared as a deterministic-CBOR value (the text `"5"` and the integer `5` are different identifiers; nested identifiers are not consumed). Consumption does not depend on the presentation time. The ALLOW record lists the consumed keys. A DENY consumes nothing. | §4.10 | only (policy, agent, nonce) consumed |
| **S11 Offline verification** | Uses no wall clock. Requires everything in S3–S9 that can be checked from the artifacts, plus a non-empty common interval (S2). An optional evaluation instant `at` must be accepted by the S2 rule. | §4.12, O3 | per-ratification window only; until round 2 of v1.2 `at` had to satisfy `lo <= at` (no tolerance) |
| **S12 Logging failures** | A failure to log never turns into ALLOW. If a denial cannot be logged, the call still returns DENY. | §4.7, I5 | an unloggable denial could raise |
| **S13 Gate–audit consistency** | The gate applies S2 to its own clock `now`. Hence, for every instant `t` (ignoring replay and payload binding): the gate allows at `t` **iff** `verify_record_offline(…, at=t)` succeeds, and every ALLOW also passes offline verification without `at`. `test_sar_properties` and `test_sar_cross` check this equivalence at every interval bound of every generated scenario, for both implementations. | §4.12 (auditors must be able to verify the authorization), O5 | an ALLOW could fail later offline verification (one approval issued within the skew window after another had expired); until round 2 of v1.2 also `offline(at=now)` could reject an ALLOW |

## Operational rules (sar_cose; not decision semantics)

| Rule | Decision |
|---|---|
| **O-a At most once** | Consumption of the replay keys and the ALLOW record are one database transaction, committed before the gate returns ALLOW. The executor acts only after ALLOW (consume-then-execute). A crash after the commit therefore leaves the authorization consumed and unexecuted; it is never re-enabled (`RollbackAndCrash.test_crash_at_every_statement_allows_at_most_once` injects a failure at every database statement). An ALLOW record means "consumed", not "executed": execution evidence is separate (paper §4.12). |
| **O-b Exact bytes** | `Gate.authorize_bytes(payload_bytes, …)` accepts only deterministic CBOR, digests a private copy and returns exactly that copy on ALLOW. The executor must send those bytes; executing a separately held or re-encoded object reintroduces T4. |
| **O-c Rollback anchor (optional)** | Without an anchor, anyone who can write the database file can re-enable a consumed authorization by restoring an older copy or deleting consumed keys (demonstrated by `test_rollback_without_anchor_reenables_a_consumed_authorization`). With `Store(path, signing_key=…, anchor=FileAnchor(…) or checkpoint)`, every ALLOW first checks that the chain is intact, extends the anchored checkpoint and contains no ALLOW record with the same replay keys, and then advances the anchor before committing. A rolled-back, truncated or forked database makes every ALLOW fail with `store_inconsistent_with_anchor`. This only helps if the anchor lives in a trust domain that the attacker on the database cannot also write. The check is O(n) in the log size per ALLOW. |

## Deliberate implementation differences (not decision semantics)

- **Chain check before ALLOW.** `independent/` re-verifies the whole hash chain before every ALLOW and refuses if it is broken. `sar_cose` does so only when an anchor is configured (O-c); otherwise integrity is checked by `verify_chain` against a retained checkpoint. This can only make a difference on a database that has already been tampered with, which is outside the cross-differential's scenario space.
- **Replay key on COSE bytes.** `independent/` also consumes a key derived from the proposal's COSE bytes. Given S9, `proposal_id` determines the proposal, so this adds nothing.
- **Clock type.** `sar_cose` requires an integer `now`; `independent/` also accepts finite floats.
