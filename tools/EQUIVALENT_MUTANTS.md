# Surviving automated mutants: equivalence arguments

`tools/mutation_sweep.py` mutates `sar_cose.py` mechanically and runs the full suite against each mutant. Every surviving mutant is either a missing test or **decision-equivalent**: no input makes the gate, the offline verifier or the store decide differently from the original. For some survivors the denial *reason* or the exception type on an internal path may differ; the decision does not.

**Machine classification (v1.3).** Each row below has an argument id (`EQ-nn`). `tools/equivalent_mutants.json` lists, for each id, the exact survivors it covers (module, mutation kind, mutation text and the stripped source line). `tools/mutation_sweep.py --json …` classifies every survivor as `equivalent` (with its argument id) only on an exact match against that file, and as `live` otherwise; a live survivor is either a missing test or a new argument that has to be written here first. The latest classified sweeps are archived in `results/` (see `results/README.md`); the paper's figures are taken from there. The arguments are written by hand and are not machine-checked: the classifier checks only that each survivor has been *assigned* an argument.

Sweep of round 2 of v1.2 (the arguments below were written against it): 476 of 491 mutants killed (96.9%), 15 survivors (line numbers refer to that version of `sar_cose.py`, which is unchanged in v1.3). Each argument is a claim that can be attacked. If you find an input that distinguishes a mutant from the original in a decision, that is a bug report.

| EQ-01 | 66 `_head`: `if n < 0: raise` | delete | `_head` is only called with lengths, tags and non-negative integers (`dcbor` maps negatives to `-1 - n`), so `n < 0` is unreachable. |

With `or`, a list of wrong length passes the check and then fails the unpack. |

The checks that are redundant here are kept on purpose. Each gives a specific denial reason and guards against future changes that remove the rule implying it.

## sar_scitt.py (v1.3)

First sweep (archived as `results/sweep_sar_scitt_first.json`; run with the same tool, before `tools/archive_run.py` was applied to sweeps): 415 of 503 mutants killed, **88 live survivors** and no equivalence arguments yet. They exposed real test gaps: malformed Receipt structures were not tested, nor audit paths with trailing or missing elements, the right-edge branch of the audit-path walk, proposal faults at the Transparency Service (attacker-chosen `proposal_id`, unauthorized agent, proposal bound to another policy, ratified proposal with a bad signature), binding with the right digest but the wrong id at the TS, touching intervals at the TS, a rejection issued at the proposal's expiry, `Registration` results, a receipt denial that could not be logged (a mutant returning ALLOW there survived), the data-item interface without a Receipt, the policy setter (revocation) and wall-clock default of `ReceiptGate`, edge cases of the consistency verifier, and malformed Transparent Authorization Records. `test_sar_scitt.SweepGaps` adds a test for each. The second sweep left 23 survivors, argued below. Line numbers refer to `sar_scitt.py` as committed in step 3 of v1.3.

## What the mechanical sweep does not generate

The sweep applies syntactic operators (comparison swaps, Boolean swaps, negations, constant changes, statement deletion). It did **not** generate the semantic security mutants that the hand-written mutants and the external audit wrote, for example: a replay key that includes the presentation time (`replay_key_with_time`, audit N09), a digest comparison over the first 8 bytes only (`digest_prefix_only`, N07), case-insensitive nonce or policy-id comparison (`nonce_casefold`, `policy_bind_casefold`, N02, N12), non-atomic consumption of replay keys (`split_consume_tx`, N15), consuming only text transaction ids (`txn_key_str_only`, N16), accepting the polymorphic `-8` algorithm at the gate (N13), or a skew constant of an hour (N01). Seven of these survived the v1.2 first-round suite although that suite killed 431 of 444 mechanical mutants. A high mechanical mutation score therefore did not imply that the security-relevant semantics were tested; the hand-written and audit mutants are a separate, necessary check, and the paper reports this as a finding (§6.4).
